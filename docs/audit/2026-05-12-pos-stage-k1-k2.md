## Part B — K1 audit findings (Returns / Refund engine)

`process_pos_return` is the only path that mutates pos_transactions for
a return. The 10-point enterprise checklist:

| # | Check | Server enforcement | Notes |
|---|---|---|---|
| 1 | Original sale required | YES — RPC errors `original_not_found` if `p_original_transaction_id` doesn't resolve | Dialog forces lookup before items step |
| 2 | Per-line over-return refused | YES — `v_pos_returnable_qty.returnable_qty` accumulates prior returns; RPC errors `over_return` | UI cap previously used `sold_qty`; Stage K1 swaps it to `returnable_qty` |
| 3 | Multiple returns against same sale | YES — view subtracts every prior completed return | Locking at row level inside the RPC |
| 4 | GL reversal correct | YES — RPC writes the matching reversing JE through the trigger that posts pos sales | Verified by inspection of journal lines on a test return |
| 5 | Inventory restoration to register branch | YES — RPC selects warehouse from `pos_shifts.warehouse_id`, falls back to default warehouse for the register's branch; writes `stock_movement` `pos_return` | |
| 6 | Refund tender control | YES — `assert_manager_override('cross_tender_refund', …)` when refund tender ≠ original tender | UI previously hardcoded "cash"; Stage K1 preselects largest original tender |
| 7 | Return reason required + per-reason override | YES — `requires_note`, `requires_manager_override` per reason | Reasons UI already wired |
| 8 | Refund receipt watermarked | NO — `ReceiptPreviewDialog` only watermarked VOID | Stage K1 adds REFUND watermark |
| 9 | Return appears in History/Net Sales | YES — already filterable | |
| 10 | Manager override matrix gates above-threshold | YES — `assert_manager_override('refund', total, …)` | |

### Stage K1 changes (UI / UX only — RPC contract unchanged)

- `src/hooks/pos/usePOSReturnableQty.ts` — new hook reads
  `v_pos_returnable_qty` for a given transaction. Returns
  `Record<original_item_id, returnable_qty>`.
- `src/components/pos/ReturnDialog.tsx`:
  - imports the new hook
  - `+` button is disabled at `returnable_qty` instead of `sold_qty`
    so the cashier can never click past what the server will accept
  - `useEffect` preselects `refundMethod` based on the largest original
    tender (cash/card/voucher); cross-tender (mobile/M-Pesa/bank) still
    falls back to cash and triggers the manager-PIN gate
- `src/components/pos/ReceiptPreviewDialog.tsx`:
  - new optional props `is_refund`, `original_transaction_number`
  - REFUND watermark renders when `is_refund && !is_voided`
- `src/components/pos/TransactionHistoryDialog.tsx`:
  - passes `is_refund` (transaction_type==='return') and
    `original_transaction_number` into ReceiptPreviewDialog so reprinted
    refund receipts visibly differ from sale receipts

### What did NOT change

- `process_pos_return` SQL — already enforces the full checklist
  server-side. Stage K1 is purely UX hardening so the cashier never
  hits a server-side rejection by accident.
- Manager override matrix — unchanged.
- Inventory writer — unchanged.

## Part C — K2 Void taxonomy (decision record)

Three semantically distinct flows previously shared the "Void" label.
The taxonomy is now:

| Action | When allowed | GL impact | Inventory impact | Manager PIN | Audit row |
|---|---|---|---|---|---|
| **Cancel cart** | Before payment dialog opens | None | None | No | None |
| **Void** | After payment, same OPEN shift | Inline reversal (no separate JE) | Restore via `pos_return` movement | Per `void_above_threshold` matrix | `pos_transactions.voided_at + void_reason_id + void_override_id` |
| **Return / Refund** | Different shift, closed shift, or cross-tender | NEW reversing JE; original posting stays | Restore via `pos_return` movement | Per `refund` / `cross_tender_refund` matrix | New `pos_transactions` row with `transaction_type='return'` |

### Server invariants already in place (verified)

- `process_pos_void` errors `shift_not_open` if the source transaction's
  shift is not currently open. The cashier is told to use Returns.
- `process_pos_void` errors `return_exists` if any non-voided return has
  already been processed against the source transaction.
- `process_pos_void` errors `already_voided` and `invalid_status` for
  defensive cases.
- `process_pos_return` errors `original_voided` so a void+return loop is
  impossible.

### What was NOT changed in this slice

- VoidTransactionDialog still surfaces the server's `shift_not_open`
  error as a toast. Auto-routing the cashier into ReturnDialog when
  this fires is a UX polish step deferred to a future slice (it
  requires plumbing the `registerId` / `shiftId` props through
  TransactionHistoryDialog and is outside the K1+K2 scope agreed in
  the plan).
