## Wave G4 — pgTAP-style runtime test for governance modes

New file `supabase/tests/governance_mode_tiers_test.sql` asserts the
three-tier semantics introduced in G3 against a synthetic
org/business/branch wrapped in a rolled-back transaction:

1. **solo + 1 member** — owner self-approval on a `bills` row succeeds
   (covers the `sod.self_action_auto_allowed` branch).
2. **auto-promote** — adding a second active `user_roles` row flips
   `organizations.governance_mode` from `solo` → `standard` via
   `trg_promote_governance_mode_on_member_add`.
3. **standard** — owner self-approval allowed (warn), staff self-approval
   blocked with `SQLSTATE 42501` / `HINT GOV_SELF_ACTION`.
4. **strict** — owner self-approval blocked.
5. **explicit override** — an `allow` row in `self_action_policy` scoped
   to `owner` lets the owner self-approve while strict mode keeps staff
   blocked (explicit row > mode default).

Run with `psql -f supabase/tests/governance_mode_tiers_test.sql` against
a database that has Wave G2/G3 migrations applied. Output ends with
`SoD Wave G4 runtime invariants: ALL OK` and the transaction is rolled
back so no test data persists.

## Wave G5 — Sensitive Field Framework (bank account routing)

The G2 deferred list flagged "vendor bank account sensitive fields" as
open. Investigation showed `contacts` doesn't actually carry vendor
banking details (payments use `bank_accounts.id` for the org-side
account). The genuine money-routing risk in the current schema is
silent modification of `bank_accounts.account_number` /
`bank_accounts.routing_number` — change those and the next payroll or
vendor payment lands in a different account.

### Schema (migration `20260611…`)

- `public.sensitive_field_audit` — append-only log of every change to a
  registered sensitive column. Stores masked old/new values (last 4
  chars visible), the actor, an optional FK to the override that
  authorized the change, and the originating `action_key`. RLS allows
  owners / super-admins / admins to read their org's rows;
  service_role has full access.
- `public.mask_sensitive_value(text)` — immutable helper that produces
  the `********1234` representation used in the audit log.
- Trigger `sod_bank_accounts_guard` (BEFORE UPDATE on `bank_accounts`):
  if `account_number` or `routing_number` changed, calls
  `governance_assert_not_self(actor, actor, 'bank_account.sensitive_change', org, 'bank_account', NEW.id)`.
  Subject = actor means it always trips the self-action evaluator,
  so the org's governance mode determines the outcome:
  - `solo` → auto-allowed + `sod.self_action_auto_allowed` event.
  - `standard` → owners/admins warn (audited), staff blocked.
  - `strict` → blocked unless a fresh co-signed override exists.
  Once the governance call returns, one row per changed column is
  written to `sensitive_field_audit`, linked to the override id if
  one was just consumed.

### Catalogue + UI

- `src/lib/governance/selfActionCatalogue.ts` registers the new
  `bank_account.sensitive_change` action under the Finance module so
  it appears in Settings → Governance → Advanced and in the override
  picker. The new `bank_account` entity type joins
  `ENTITY_TYPE_LABELS` and `ENTITY_TYPE_DB_KEY`.
- `src/test/architecture/sod-coverage.test.ts` ACTION_TO_TABLE map
  extended so the architecture guard now requires the
  `sod_bank_accounts_guard` trigger to exist.

### What's verified
- Migration applied cleanly; the linter warnings emitted are all
  pre-existing and unrelated to this wave.
- New trigger fires only when one of the two registered columns
  actually changes (driven by `IS DISTINCT FROM`).
- Override consumption + audit linkage tested manually against a
  synthetic org in strict mode.
- Architecture coverage test still green; it now also pins the bank
  account guard.
