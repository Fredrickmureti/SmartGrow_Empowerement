# Phase 2 + 3 + 4 — Outbound Lot Awareness (closeout)

Migration: `20260530140323` (timestamp generated by Lovable).
Frontend is parked; this loop ships backend only.

## Plan deviation from `.lovable/plan.md`

The plan originally targeted `convert_*_to_invoice_atomic` for Phase 2, but
`pg_get_functiondef` walk showed those RPCs only create draft paperwork — they
never write `stock_movements`. The real outbound surface is
`complete_delivery_atomic` (called by `confirm_invoice_and_release_stock_atomic`).
Phase 2 was retargeted accordingly. Defaults adopted: **1a** (delivery-note-only
columns, defer `invoice_items`/`sales_order_items`) and **2a** (auto-FEFO
silent fallback when caller didn't supply allocations).

Phase 3 (POS) and Phase 4 (adjustment normalisation — already shipped via the
existing branch in `approve_stock_adjustment_atomic`; this loop adds
`pos_return` to the trigger's in list as the equivalent fix for POS) were
folded into the same migration since they share the same trigger contract.

## Changes

### Trigger
- `_maintain_warehouse_stock_lots` now classifies `pos_return` as inbound
  (added to the `v_is_in` list). Previously POS returns of lot-tracked
  products silently skipped `warehouse_stock_lots`.

### Schema
- `delivery_note_items`: added `lot_allocations jsonb`, `lot_number text`,
  `serial_number text` (idempotent `IF NOT EXISTS`).
- `pos_transaction_items`: added the same three columns.

### RPCs
- `complete_delivery_atomic`
  - Lot-tracked branch: honours caller `lot_allocations`, else auto-FEFO
    via `resolve_fefo_lots`, persists the picked allocations on the line,
    and calls `consume_lots_atomic('delivery', 'delivery_note', dn_id, ...)`.
  - Non-lot-tracked branch: unchanged single-movement insert.
  - COGS math unchanged (same `v_unit_cost * qty` rollup, same journal
    entry).
- `process_pos_transaction`
  - Sale + lot-tracked product: caller-or-FEFO allocations, persisted on
    `pos_transaction_items.lot_allocations`, consumed via
    `consume_lots_atomic('pos_sale', 'pos_transaction', tx_id, ...)`.
  - Idempotent replay path untouched (early return on existing
    `idempotency_key`).
  - Non-lot or non-sale branches unchanged.
- `process_pos_return`
  - For lot-tracked products: replays the original sale's
    `lot_allocations` from `pos_transaction_items`, takes the first
    matching `qty` to cover the return quantity, persists those
    allocations on the new return-line row, and writes one
    `pos_return` movement per allocation (so `warehouse_stock_lots` grows
    back into the correct batches).
  - Non-lot-tracked: unchanged single aggregate movement.
