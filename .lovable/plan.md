# Client Profile — Read-Only Detail View, Deliberate Edit

Standalone wave. Nothing from the branch / loan officer / group registration wave is revisited: `mf_register_client`, officer-branch filtering and group assignment on registration stay exactly as they are.

## A. What happens today (verified)

In the client register (`src/apps/lending/clients/ClientsPage.tsx`), clicking any row calls `openEdit(client)` which opens `ClientFormDialog` — the very same dialog used for registration, prefilled and fully editable on the first click. There is no read-only client view anywhere in the lending module.

Saving from that dialog writes straight to the client table with a direct update of whatever the form holds — including branch, loan officer and status.

## B. What the record actually allows (verified)

- Database access rules on the client record are already correct and scoped: read, create, update and delete are each checked against business, branch and — for own-portfolio officers — the owning officer. The UI is not the security boundary and does not need to be.
- The client number is generated by the database on registration; the form never sends it back.
- Group membership is not stored on the client at all. It lives in the group membership records, with a database rule allowing only one active group per client. Registration handles the first assignment; there is no generic client update path to group.
- Completed cycles, joined date and timestamps are maintained by the system, never by this form.
- There is no dedicated branch-transfer or officer-reassignment operation in the system today, and no audit history for client changes.

## C. Field classification

**Ordinary editable profile information** — name, national ID, date of birth, gender, phone, email, physical address, occupation, business type, business location, next-of-kin name/relationship/phone, notes, KYC photos.

**Controlled — deliberate action, not a casual dropdown** — branch, loan officer, status. Each carries operational meaning: branch and officer decide who may see and work the client and who collects; status affects whether the client can take loans.

**Derived / system-owned — never editable** — client number, institution, joined date, completed cycles, created/updated timestamps.

**Owned by another workflow — absent from client editing** — group membership (group management), fees and charges (existing charges screen), loans, applications and repayments.

## D. Downstream impact

Changing branch or officer moves the client out of one person's portfolio and into another's — it can make the record invisible to the officer who was working it, and it changes which branch the client's collections belong to. Status changes gate lending eligibility. Ordinary contact and KYC details carry no lending or accounting consequence. Nothing in the profile touches ledgers or balances.

## E. Target experience

```text
Client list
   -> click a client
Client detail sheet  (read-only, current stored record)
   -> "Edit client"
Client edit form (profile fields)
   -> Save  -> back to the detail sheet, refreshed
   -> Cancel -> discards changes, back to the detail sheet
```

No "are you sure you want to edit" prompt. The Edit button is the deliberate act. A confirm is used only when leaving with unsaved changes.

Controlled fields appear on the detail sheet as plain information with their own small actions — "Change branch", "Reassign officer", "Change status" — each a short focused dialog with a reason note, rather than dropdowns sitting inside the general profile form.

## F. Frontend changes (minimum set)

1. New `ClientDetailSheet` in `src/apps/lending/clients/` built on the existing detail-drawer primitive: header with name, client number and status badge; sections for identity/KYC, contact, business, next of kin, and an assignment section showing branch, loan officer, and current group (read from the existing active-group hook). Footer: Close and Edit client (Edit only for users with client-management permission).
2. `ClientsPage`: row click opens the detail sheet for everyone who can view clients — not the edit form, and no longer conditional on manage permission. Registration button unchanged.
3. `ClientFormDialog`: keep as-is for registration; in edit mode drop branch, loan officer and status from the form body and from the saved payload, and open it only from the detail sheet. Cancel with unsaved changes asks once before discarding; a successful save returns to the detail sheet.
4. Three small controlled-change dialogs (branch, officer, status) opened from the detail sheet, each visible only with client-management permission and each restricted to the branches/officers the user may actually use.
5. All failures keep using the existing lending error translator — no new error handling, no raw database text, no `[object Object]`.

## G. Backend changes

The access rules on the client record already enforce institution, branch and own-portfolio on both read and update, so no policy change is needed. Two additions:

- A database guard that refuses to change the client number, institution, joined date and completed cycles through an ordinary update, so hiding them in the UI is backed by the server.
- Client changes recorded in the existing lending event/audit trail — a compact record of who changed what and when, focused on the controlled fields (branch, officer, status). No new audit subsystem.

## H. Tests

Backend checks run directly against the database for: cross-institution and out-of-branch update rejection, own-portfolio officer rejection on another officer's client, and rejection of system-field tampering.
