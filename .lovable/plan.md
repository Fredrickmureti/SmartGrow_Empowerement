# POS receipt parity and 58mm conformance remediation

## Verified diagnosis

- **The header divergence is in our system, not EscPosEmulator.** The reported centered `#POS…` plus `Status:` exactly matches the surviving legacy implementation in `_shared/escpos/builder.ts`. The canonical receipt AST renders `No: …`, and both the current thermal PDF and current ESC/POS renderer consume that AST.
- **The local print agent is byte-transparent.** It sends the generated byte array to the configured socket without changing margins, columns, font, or content.
- **The overflow is a printer-profile contract mismatch.** The saved ESC/POS artifact for the affected transaction is explicitly tagged `font: B, columns: 42`. A 58mm profile is not universally 42 columns: 42 requires Font B support and correct handling of `ESC ! 0x01`; the safe interoperable baseline is Font A at 32 columns. If EscPosEmulator displays the stream with Font A metrics or ignores Font B, a 42-column row necessarily overflows/wraps.
- **Current source routes new POS ESC/POS generation through `renderDocumentEscPos`, but legacy code remains importable and old immutable artifacts/deployments can retain the old shape.** Existing tests prove imports, not full rendered-content parity or artifact-version behavior.

## Enterprise defaults

- POS receipts use one canonical `Line[]` AST for preview, thermal PDF, and ESC/POS.
- The clean PDF behavior becomes canonical: `No: <transaction number>` and no routine `Status:` row on completed POS receipts.
- Uncalibrated 58mm output defaults to **Font A / 32 columns**. Font B / 42 columns is allowed only through an explicit, validated printer profile.
- Issued artifacts remain immutable for audit. “Reprint original” preserves historical bytes; “render current layout” is a distinct operation and creates a new versioned artifact rather than silently mutating history.

## Implementation

1. **Close the legacy receipt path**
   - Remove production POS-receipt access to `buildDocumentEscPos` and restrict the legacy builder to non-POS legacy fixtures/specialized paths that still require it.
   - Expand the architecture guardrail so any receipt-like production caller importing the legacy builder fails CI.
   - Keep kitchen-ticket ownership separate.

2. **Make one resolved render contract**
   - Extract the duplicated paper/font/columns/margins resolution currently present in preview/test-print and real-document branches into one pure resolver.
   - Feed its single resolved profile into both `buildReceiptLines` and artifact metadata; stop independently recomputing observability headers.
   - Preserve precedence, but make every dropped or overridden profile value explicit in diagnostics.

3. **Apply safe 58mm behavior**
   - Use 32 columns / Font A when a 58mm target has not passed calibration.
   - Permit 42 columns / Font B only when the selected physical profile explicitly declares that capability.
   - Update the affected EscPosEmulator/local profile to the safe baseline so the immediate output cannot exceed the emulator’s printable grid.
   - Clamp emitted rows to the resolved grid after margins and verify no text row exceeds it.

4. **Version receipt artifacts**
   - Store `renderer_id`, `renderer_version`, paper, font, columns, margins, and layout-contract version from the actual `ReceiptLinesResult` on every ESC/POS/PDF artifact.
   - On reprint, identify legacy artifacts instead of presenting them as current canonical output.
   - Expose separate internal operations for immutable original reprint and current-layout regeneration.

5. **Strengthen parity and regression tests**
   - Add a POS fixture containing number and status; assert preview, thermal PDF input, and decoded ESC/POS lines all contain `No:` and all omit the routine status row.
   - Add 58mm conformance fixtures for safe Font A/32 and calibrated Font B/42, asserting the emitted font command and maximum row width.
   - Add tests for both persisted legacy-artifact reprint and current-layout regeneration.
   - Replace the weak structural-only parity gate with rendered line/content comparisons and a prohibition on live legacy POS imports.

6. **End-to-end validation**
   - Generate a fresh 58mm POS receipt and inspect returned renderer/profile metadata and decoded bytes.
   - Send those exact bytes through the local agent to EscPosEmulator and confirm the `No:` layout, absent routine status, 32-column bound, margins, totals alignment, and cut/feed behavior.
   - Compare the same transaction’s thermal PDF and ESC/POS normalized line sequence and retain the fixtures as CI evidence.

## Expected result

Fresh POS PDF and ESC/POS output will have the same content structure by construction. A default 58mm emulator or printer will receive Font A / 32-column-safe rows, while verified devices can opt into Font B / 42 columns without weakening the default.
