# Label Operations: from per-product buttons to a demand-driven engine

## Audit verdict

The print *transport* layer is already enterprise-grade. The label *demand* layer does not exist.

What is already correct and must be reused, not rebuilt:

- One ledger: `print_jobs`, written only through `src/services/printing/jobs.ts`.
- One server drainer: `supabase/functions/dispatch-print-jobs` (pg_cron, claim-with-SKIP-LOCKED, back-off, DLQ, render → route → ack).
- One hardware seam: `PrintService` → `dispatch.toDevice` → `resolve_device` → local adapter or `edge_jobs` relay to an IoT agent; readiness via ADR-0113.
- One rendering owner per medium (ADR-0085), one barcode-identity rule (`resolveLabelBarcode`, refuses on missing level identifier — ADR-0089/0102), one template registry (`label_templates`, org/branch scoped, versioned).
- One caller seam: `useLabelPrint` / `PrintLabelButton`, used by Products, POS, LotDetail, PutawayQueue, PackStation, CountSession, mobile receiving, FixedAssets.

What is missing, and is the actual problem:

1. **Label demand is not modelled.** There is no entity meaning "these 4,300 SKUs need a shelf label because prices change on Monday". Demand only exists as a click on one product row.
2. **Bulk is a client `for` loop.** `BinLabelDialog` awaits `print()` per location in the browser. At 50,000 labels this is 50,000 round trips, a blocked tab, no resume, and no single audit object.
3. **Label events are absent from the event fabric.** `business_event_topics` has `inventory.*`, `procurement.*`, `pos.*`, `payment.*`, `legal_order.*` — no `label.*`. Goods receipt, price publication, product import and barcode enrollment cannot express label consequences.
4. **Label data is assembled client-side.** Price, pack level and identity are gathered per item in React. Any batch of size N causes N lookups and duplicates pricing rules in the frontend.
5. **No operator workspace.** Platform → Hardware owns devices, media, templates and print activity. There is no inventory-facing place to see what needs labelling, approve it, and track a run.

Conclusion: keep the whole execution pipeline; add a demand and orchestration layer above it, and make bulk a server-side set operation.

## Target architecture

```text
Business events (GRN, price publish, import, enrollment, promo, recount)
        |                                       operator selection / saved filter
        v                                                  v
                 label_demand (what needs labelling, why, when)
                                   |
                          Label Run (approve / scope / copies)
                                   |
              server-side expansion: one set-based SQL query
              (product + identity + packaging + price + template)
                                   |
                     print_jobs  (existing ledger, existing RPCs)
                                   |
                dispatch-print-jobs  ->  render -> resolve_device
                                   |
                        local adapter | edge_jobs relay -> IoT agent -> printer
```

Ownership boundaries:

- **Label Engine (new, server)** owns *what* to label and *how many*.
- **Print pipeline (existing)** owns *rendering*, *routing* and *delivery*. Unchanged.
- **UI** owns selection and monitoring only. No pricing, no identity, no batching logic.

## What changes for users

- Product row keeps **Print label** / **Print shelf label** — they become one-line runs submitted to the engine, with identical instant behaviour.
- New **Inventory → Label Operations** workspace:
  - *Needs labels* — demand generated by business events (new stock received, price changed, barcode enrolled, imported), each with reason, age and count.
  - *Runs* — create from a selection or a saved product filter, choose template, copies, printer workflow and branch; live progress, pause, cancel, retry-failed, reprint.
  - *Templates* and *Print activity* deep-link to the existing Hardware screens rather than duplicating them.
- Multi-select on the Products grid and warehouse location tree feeds a run instead of looping prints.

## Technical plan

### Phase 1 — Domain model (migration)

- `label_demand`: business_id, branch_id, entity_type (`product` | `location` | `lot` | `carton` | `pallet`), entity_id, reason (`goods_receipt` | `price_change` | `barcode_enrolled` | `product_import` | `promotion` | `recount` | `manual`), suggested_template_key, source_event_id, qty_hint, status (`open` | `queued` | `dismissed`), timestamps. Unique on (business_id, entity_type, entity_id, reason, open) so repeated events coalesce instead of fanning out.
- `label_print_runs`: business_id, branch_id, warehouse_id, template_key, workflow, copies, selection_spec jsonb (filter predicate, *not* a materialised id list), status (`draft` | `expanding` | `running` | `paused` | `completed` | `failed` | `cancelled`), counters (total, queued, printed, failed), created_by, timestamps.
- `label_print_run_lines`: run_id, entity_id, resolved_vars jsonb, print_job_id, status, error. Indexed on (run_id, status).
- GRANTs for `authenticated` + `service_role`, RLS scoped by `user_business_access`, writes gated by inventory/warehouse roles via `has_role`.

### Phase 2 — Expansion engine (SQL + edge)

- `expand_label_run(run_id, batch_size)` SECURITY DEFINER: resolves the selection spec into run lines with a single set-based query joining products, `product_identifiers` (active only, via the canonical lifecycle predicate), `product_packaging`, price and template. Refuses rows with no level identifier and records the refusal reason on the line — never falls back to a SKU or UUID (ADR-0089).
- Chunked, resumable, idempotent: repeat invocations continue where they stopped; a run of 50,000 expands in bounded batches.
- Lines are converted to `print_jobs` rows through the existing insert RPC with a deterministic idempotency key (`run_id:entity_id:copy_index`), so the existing drainer does the rest untouched.
- `dispatch-label-runs` edge function on pg_cron drives expansion and rolls up counters. Job execution stays with `dispatch-print-jobs`.

### Phase 3 — Event fabric

- Register `label.demand.raised` and `label.run.*` in `business_event_topics`.
- Consumers that raise demand, reusing existing producers: goods receipt posting, price publication, barcode enrollment completion, product import completion, promotion activation, physical-count approval. Each writes `label_demand` — nothing auto-prints. Printing always requires an operator-approved run.

### Phase 4 — Client seams

- `useLabelRun()` — create, monitor (realtime on the run row), pause, cancel, retry-failed.
- `useLabelDemand()` — grouped demand counts and dismissal.
- `useLabelPrint` is refactored to submit a single-line run; its refusal rules, toasts and missing-device CTA are preserved so every existing caller and every guard test keeps passing.
- Guard tests extended: no page may build a label batch loop; batch entry must go through `useLabelRun`.

### Phase 5 — UI

- New route `inventory/label-operations` with Demand, Runs and Run detail views, built from existing design-system primitives.
- Products grid and warehouse location tree gain "Print labels for selection" that opens the run composer.
- `BinLabelDialog` is re-pointed at a run; its per-location client loop is deleted.

### Scale characteristics

- Selection stored as a predicate, so a 2M-SKU run never ships ids through the browser.
- One query per expansion batch — no N+1, no per-item price fetch.
- Rendering and device resolution stay where they already are, so 100 printers and 400 users reuse the proven relay.
- Every run is resumable and idempotent; a crashed tab or a dead workstation loses nothing.

## Out of scope

- No change to rendering, ESC/POS, ZPL, media geometry, device registry or readiness.
- No new barcode library, no client-side rasterisation.
- No automatic printing without operator approval.
